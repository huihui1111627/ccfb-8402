# 幂等与断点续跑设计

本文解释「为什么同一人不会被提交两次」，以及会话过期、进程崩溃、结果未知这些边界情况分别怎么处理。

## 1. 业务指纹

```
fingerprint = SHA256(企业编码 | 险种 | 证件号 | 变更类型 | 生效月份)[:20]
```

刻意**不包含金额**：同一人同月对同一险种的「基数调整」若先后报了两个不同金额，业务上仍是一次申报，第二次属于重复申报事故，必须人工走更正流程，而不是系统自动再提一次。

因此，人工在控制台修改基数不会改变指纹，重跑仍会落在同一条 claim 与站点同一条唯一约束上；只有修改证件号或生效月份才会生成新指纹（此时系统会取消旧任务、另建新任务，并在审计日志里记录 `fingerprint_changed`）。

## 2. 四层防线

### 第一层：导入期判重（`app/importer.py` / `create_task`）

导入时按指纹查已有任务：

- 已有 `success` / `duplicate` 记录 → 返回 `duplicate_success`，**不建任务**，记一条 warning
- 已有未完成任务 → `merged`，复用原任务，更新 payload
- 已有失败/待修正/已取消 → `requeued`，清错误重新排队
- 否则 `created`

同一份花名册导入两次，第二次不会产生任何新任务。

### 第二层：数据库 claim 唯一（`app/db.py`）

```sql
CREATE UNIQUE INDEX ux_tasks_claim ON tasks(fingerprint) WHERE claim_token IS NOT NULL;
```

`claim_task` 用一条 `UPDATE ... WHERE status IN (...) AND (claim_token IS NULL OR claim_token=?)` 原子抢锁，抢到才写入 `claim_token`。两个 worker 同时抢同一指纹，只有一个能成功，另一个得到 `race_lost`。

即使数据库里因为历史脏数据存在两条同指纹任务，它们也不能同时持有 claim；后完成的那条在提交前会被站点核对拦下。

### 第三层：提交前后两次站点核对（`app/runner.py`）

每次执行：

```
登录
  → 核对（按指纹查站点）─── 查到 → 直接采纳回执，结束
  → 填表（可因会话过期原地重登重放）
  → 核对（第二次）─────── 查到 → 直接采纳回执，结束
  → 标记 submitting
  → 点击提交
```

核对走站点查询接口（`/mock/{window}/query?fingerprint=`），只读，带浏览器会话 Cookie。会话过期时重新登录再查，不会产生副作用。

### 第四层：站点唯一约束

Mock 站点对 `(window, enterprise_code, fingerprint)` 建唯一索引，重复提交会返回**同一条已受理记录**（真实政务系统通常也这样幂等受理）。这层是兜底：万一前面都失效，站点也不会受理第二笔。

## 3. 提交动作的状态机

```
pending ──claim──▶ running ──填表──▶ submitting ──成功──▶ success
                        │                  │
                        │                  ├─响应丢失/掉线─▶ unknown ──核对──▶ success
                        │                  │                     └─查无记录且未超次─▶ retry
                        │                  │                     └─查无记录且超次──▶ needs_fix
                        │                  └─站点校验失败─▶ needs_fix
                        └─会话过期─▶ 原地重登重放（不消耗尝试次数）
```

关键规则：

- `mark_submitting` 在点击之前落库。进程若在此阶段崩溃，重启后 `reconcile_orphans` 把 `running` 置为 `unknown`，执行时**先核对**，绝不直接重提。
- 点击之后出现任何非确定结果（导航超时、跳到登录页、没有回执页）都抛 `SubmitOutcomeUnknown`，进入只读核对循环。
- 提交点击前的最后守卫检查当前页确实是提交页、且证件号与生效月份与任务一致，否则中止提交。

## 4. 会话过期续跑

站点 10 分钟过期。两种情况：

**填表过程中过期**：表单 POST 后 303 回登录页，驱动抛 `SessionExpired`。引擎原地重新登录（取码时带 `since_id`，避免复用旧验证码），然后从第 1 步重放到提交受理页。重放只是填表，不提交，所以不会重复申报；并且不消耗重试次数。

**提交点击后过期**：点击已经发生，无法确定站点是否受理。驱动同样抛 `SubmitOutcomeUnknown`，引擎重新登录后按指纹核对：查到就采纳，查不到才重排。

## 5. 为什么重放安全

重放只调用 `fill_and_continue` 与 `confirm_step2`，两者都不点提交按钮。重放结束后引擎会再做一次站点核对，然后才决定提交。所以「重放」最多导致一次多余的草稿，不会导致一次多余的申报。

站点侧草稿（`mock_drafts`）与会话解耦，但引擎不依赖跨会话草稿：续跑一律从第 1 步重填，因为真实站点通常也不保证草稿持久化。

## 6. 观测与审计

- `tasks.checkpoint` 记录当前阶段与草稿号
- `executions` 每次尝试一行，含状态、错误码、截图清单
- `audit_events` 记录导入、执行、修正、重排、跳过、取消、归档失败等
- 回执台账 `ledger.jsonl` 用 prev 哈希串成链，任何一条被改都能被发现

## 7. 已知边界

- **站点不做幂等受理、且查询接口不可用**：只能靠本地 claim 与提交前核对。这种情况需要在提交后立刻抓取回执号并落库，窗口期仍然存在。生产对接时优先确认站点是否提供按业务流水号查询的接口。
- **同一份花名册里同一指纹出现两次**：导入期合并，只建一条任务，warning 里给出重复行号。
- **人工在站点手动办了同一笔业务**：如果发生在引擎执行前，核对会直接采纳；如果发生在引擎提交的同一时刻，站点唯一约束兜底。
- **修改了证件号**：视为新业务，另建任务；旧任务取消并在审计日志留痕。这通常意味着花名册原本就填错了，需要人工确认。
